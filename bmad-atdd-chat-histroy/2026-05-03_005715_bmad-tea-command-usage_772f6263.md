## Test Design: Coverage Strategy

I recommend a **risk-based pyramid** — test the highest-risk scenarios thoroughly, lower-risk scenarios with spot checks:

### Layer 1: API Contract Tests (Unit + Integration) — **FOUNDATION**
**Goal:** Validate tenant scoping at the service layer before any UI touches it.  
**Criticality:** HIGHEST — catches bugs cheapest and fastest.

**Test Scope:**
- ✅ **GET /api/tasks** — when called by User A from Tenant 1, returns only Tenant 1's tasks
- ✅ **POST /api/tasks** — User A cannot create task assigned to Tenant B (tenant_id validation)
- ✅ **GET /api/tasks/{taskId}** — if taskId belongs to Tenant B, returns 403 Forbidden (not 404 — no info leak)
- ✅ **GET /api/admin/users** — admin from Tenant 1 sees only Tenant 1's users
- ✅ **PATCH /api/users/{userId}** — cannot update users from other tenants
- ✅ **Database query isolation** — ORM query builder auto-filters by tenant_id
- ✅ **Error handling** — API returns generic 403 (no "Tenant not found" or task details)

**Recommended Tools:** Playwright API testing or native fetch in Node.js  
**Complexity:** Medium (requires test data setup: 2 tenants, 2 users, mock tasks)

---

### Layer 2: Session & Permission Tests (E2E) — **VALIDATION**
**Goal:** Verify that a user's session is bound to one tenant and cannot escape via UI manipulation.

**Test Scope:**
- ✅ User logs in to Tenant A, receives session token with tenant_id embedded
- ✅ User manually changes URL/parameters to reference Tenant B's task — page returns 403 or empty state
- ✅ Session token is invalidated if tenant changes (e.g., via force logout)
- ✅ Admin dashboard shows correct tenant scoping in all dropdowns/searches

**Recommended Tools:** Playwright browser automation  
**Complexity:** Low (uses Playwright's existing setup)

---

### Layer 3: Admin OIDC Isolation Test — **SPOT CHECK**
**Goal:** Confirm that configuring OIDC for Tenant A doesn't affect Tenant B's authentication.

**Test Scope:**
- ✅ Tenant A admin configures OIDC with mock IdP
- ✅ Tenant B admin logs in with different IdP
- ✅ Tenant A's IdP setting is unchanged and Tenant B's login still works
- ✅ Token validation uses Tenant A's OIDC keys (not Tenant B's)

**Recommended Tools:** API tests with mocked OIDC endpoints  
**Complexity:** Medium (OIDC mocking required)

---
